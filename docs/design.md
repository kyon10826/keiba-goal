# keiba-goal 設計書 (v2)

普通の JRA 開催日に使う「券種別の確率予測 + 目標到達型 (Goal-reaching) の買い目推奨」システム。
2026 年のコンペ用コード (keiba_mlops) とは独立した新リポジトリとして 1 から作る。

- v1 作成: 2026-10-29 / v2: 同日、5 観点の独立レビュー (リーク・計算量・投票数理・ライブ運用・資料への忠実さ、指摘 62 件) を反映
- レビューの検証スクリプトと数値: `…/scratchpad/review/` (keiba_mlops セッションの scratchpad)。本文中の数値はそこで実データから測ったもの。

## 0. 目的・やらないこと・期待値

**目的**
1. 単勝・複勝それぞれの的中確率を、校正された確率として出す (券種別モデル)。
2. 1 日の予算 x0・目標額 A・その日に買う最大回数 k0 を朝に決め、各レースの判断時刻 (発走 6 分前) に「目標に届く確率を最大にする」単勝・複勝の買い目と金額を推奨する。
3. 実際に買ったかをその場で記録し、結果 (払戻) で資金を更新し、目標到達 / 回数切れ / 資金切れで終了する。

**やらないこと**
- 馬券の自動購入 (推奨の表示と記録まで)。
- JRDB など有料データ (手元データ + netkeiba の公開ページのみ。ユーザー決定 c の選択肢に netkeiba を含めて提示済み)。
- 馬連・三連系 (v1 は単勝・複勝のみ。PDF の実購入 9 回もすべて単勝)。
- 障害レース (平地のみ。全レースの 3.7%)。

**期待値 (成果報告と `day start` の表示で毎回出す)**
- 参照した 2 資料とも「モデル単体で市場に勝てた証拠はない」と結論している。SpeakerDeck の改良モデルも Brier・単勝的中率で市場に負けており (Brier 0.0586 vs 市場 0.0576、的中率 32.5% vs 33.7%)、回収率 103.55% の「EV 帯で絞る」買い方は選択バイアスのため採用しない。
- Goal-reaching は期待値がマイナスのまま「目標に届く確率」を最大化する方策。市場と同じ精度 (エッジなし) なら、既定の 1 日 (予算 10,000 円 → 目標 20,000 円、最大 3 回) は:

| 項目 | 値 |
|---|---|
| 狙うオッズ o*_3 | 4.85 倍 |
| 目標到達確率 P*_3 (理論値) | 41.8% |
| どんな買い方でも超えられない上限 1 − (1 − x/A)^0.8 | 42.6% |
| 終了時資金の期待値 | 約 8,360 円 (−16%) |
| 資金をほぼ全部失う日の割合 | 約 58% |

- P*_k は独立性・校正・一定の控除率を仮定した理論値で、保証ではない。PDF の 263.8 万到達は 1 回の結果。
- 2025-01〜2026-10 はオッズ時系列が無く、オッズ特徴量込みのモデルを正式評価できない (PDF ではこの期間に単勝モデルの劣化が見えていた)。

## 2. 実行環境

- Python 3.12 (`uv venv --python /opt/homebrew/bin/python3.12`。uv の自動選択は Anaconda を拾い、その pyarrow が NumPy 2 で壊れているため明示する)。`requires-python = "==3.12.*"`。
- 依存は `uv.lock` で完全固定してコミット: numpy, scipy, pandas (<3), polars, pyarrow, scikit-learn, lightgbm, xgboost (<3, FLAML の互換範囲), catboost, flaml[automl] (blendsearch extra は入れない), optuna, requests, beautifulsoup4, lxml, pyyaml, matplotlib, openpyxl, psutil, pytest。shap は使わない (各学習器のネイティブ寄与度で計算)。Homebrew の `libomp` が前提。
- **P0 の ML スモークテスト** (`make smoke-ml`): 全学習器を 20 ラウンド学習、FLAML を DaySplit で 30 秒、Optuna の sqlite スタディ 2 試行。FLAML が scikit-learn 1.7 で動かなければ 1.6 → 1.5 に下げる。
- マシン: Apple M2 / 8 コア / **メモリ 8GB** (計測時 空き 1.5GB・スワップ 11〜13GB・省電力モード ON・mysqld 常駐) / 空きディスク 52GB (生成物は合計 3GB 未満)。
  - **全特徴量は Float32** (1 列でも整数やカテゴリ型が混ざると LightGBM が全体を float64 にコピーする)。学習時は `np.empty((n, p), np.float32, order="F")` に年ごとに読み込み、LightGBM は Dataset を作ったら `save_binary` して元配列を解放。1 プロセスの目標ピーク 2.5GB 以下。特徴量作成と学習を同時に動かさない。
  - CatBoost は `allow_writing_files=False`。FLAML はスクラッチ用の作業ディレクトリで動かす。
  - macOS の multiprocessing は spawn。並列処理は `if __name__ == "__main__":` の内側で。
  - 長時間処理 (`train`, `day run`) の前に事前チェック: 省電力モード・空きメモリ (学習段階は 2.5GB 未満なら停止)・メモリ上位プロセスを表示し、`caffeinate -i -s -w <pid>` で自分自身をスリープから守る。README に「学習の日はブラウザ等を閉じ、`brew services stop mysql`、電源接続」を書く。
- 外部パス (config で指定、コピーしない): record_data、Time_Series_Odds、公式列仕様 xlsx (いずれも keiba_mlops 内)。
- 生成物は `data/` (gitignore): `raw/netkeiba/` (HTML, gzip) と `raw/manifest.sqlite`、`interim/` (正規化済み parquet)、`state/` (前日までの状態表)、`features/`、`models/`、`sessions/`、`backtest/`、`live_odds/`。

## 3. データ

### 3.1 成績データ (record_data, 47 列)

- 44 ファイル (1986〜2024 年次 + 2025 のスナップショット 5 本)。Shift-JIS、ヘッダ無し、全行 47 列。値の前後空白は strip。dtype は明示 (推論させない)。
- 2025 は**最新スナップショット 1 本だけ**読む (古いものは部分集合で、全部読むと最大 5 重複)。現状 `record_data_2025_20250919.csv` (2025-01-05〜09-15)。合計 1,823,189 行 / 136,239 レース。
- キー: `race_id` 18 桁 = YYYYMMDD + 場(2) + 回(2) + 日(2, A/B/C=10/11/12) + R(2) + 馬番(2)。`race_key = race_id // 100` (16 桁, = 時系列オッズのレース ID)。`nk_race_id` (netkeiba 12 桁) = YYYY + 場 + 回 + 日 + R。`date` は race_id 先頭 8 桁から (year 列は 2 桁なので使わない)。
- 異常区分 `error_code` (JV): 0 正常 / 1 出走取消 / 2 発走除外 (1999 年まで) / 3 競走除外 / 4 競走中止 / 5 失格 / 6 落馬再騎乗 / 7 降着 (着順は降着後の値)。
- `horse_N` は取消馬を含む登録頭数。ラベルと払戻規則には実際の出走頭数 `starters` (error_code ∉ {1,2,3}) を使う。**特徴量・正規化には判断時点で分かる頭数 `field_dec` を使う (§4.1)**。
- 発走前に使える列 (27) とレース後の列 (rank, time, time_diff, corner1-4, last_3F_time/rank, Ave_3F, PCI, -3F差, leg, prize, error_code, **確定 win_odds, 確定 pop**) を区別。後者は「過去走」としてのみ使う。
- `leg` (TARGET 式の脚質) は netkeiba から再現できないので使わない。通過順位から自前の先行度を全行同じ式で作る。
- `class_code` (非公式 TARGET 式) の序数マップを固定: 新馬 15 / 未出走 11 / 未勝利 7 → 0、400万下 19 / 500万下・1勝 23 → 1、900万下 39 / 1000万下・2勝 43 → 2、1500万下 63 / 1600万下・3勝 67 → 3、L 115 / OP 131 → 4、重賞(格なし) 147・G3 163 → 5、G2 179 → 6、G1 195 → 7。アラブ系 27/31/35 と 59 は学習から除外。
- `track_code` (JV) を芝ダ・回り・内外に分解 (10-22 芝, 23-29 ダ, 51-59 障害)。`corner_num` は (場, track_code, 距離) で一意に決まる (123 コース、矛盾 0)。
- 同着: 着順は (1,1,3) のように最小順位で入っている (2004 年以降の 1 着同着 92 件すべて)。よって「着順 ≤ 3」は JRA の支払対象と一致する。

### 3.2 時系列オッズ (JD / JR / JW)

- JD = 単勝 + 複勝 Lo/Hi、JR = 馬連 153 組、JW = 枠連。期間 2003-10-04〜2024-12-28。**2025 年以降は無い**。
- ファイル名: 種別(2) + 場(2) + 年(2) + 回(1) + 日(1, 16 進: A-C=10-12) + R(2)。中の 16 桁 ID = race_key。
- 列 (JD): レースID, 区分, 月日時分 (MMDDHHMM, 年なし; 年は race_key から、前日分は前日の日付), 頭数, 単勝票数, 複勝票数, 以降 馬ごとに (単勝, 複勝Lo, 複勝Hi)。0.0 は NaN。同時刻の重複行は後の行を採用。
- 区分: 1 中間 / 2 前日売最終 / 3 最終 (締切) / 4 確定。**区分 3・4 は特徴量に使わない**。
- **基準時刻と締切後の行の除去 (2022 年以降、締切後の区分 1 行が混ざる)**:
  - `ref` = **最初の**区分 3 行の時刻 (区分 3 が 2 行あるファイルがある)。
  - `close_est` = 単勝票数が確定の 99% 以上になった最初の区分 1 行の時刻。存在すれば `ref = min(ref, close_est + 2 分)`。
  - 候補行のうち単勝票数が確定の 97% 以上のものは捨てる (NaN + 欠損フラグ)。
  - `post_est` = ref − Δ。Δ (区分 3 − 発走時刻) の中央値は 2023-24 のクロールで得る発走時刻から測る (参考 0〜2 分)。2023-24 は実際の発走時刻を使う。
- **スナップショット**: T-x = 区分 ∈ {1,2} かつ上の除去を通った行のうち、時刻 ≤ post_est − x 分の最後の行。x ∈ {120, 60, 30, 6}。**判断スナップショットは T-6** (ライブは発走 6:00 前に取得。学習時の「T-5」行は区分 3 の平均 6.75 分前だったため、ライブと時計を合わせる)。鮮度上限: T-120/60 は 10 分、T-30 は 5 分、T-6 は 3 分 (超えたら NaN + 欠損フラグ)。
- 出力: `ts_snap_{year}.parquet` (race_key, horse_num, x, win, place_lo, place_hi, staleness_min, vote_share) と `ts_final_{year}.parquet` (確定単勝・複勝 Lo/Hi; 評価・下落率推定専用)。
- **オッズ下落率表 q** (判断時のオッズから払戻時までにどれだけ下がるかの控えめな見積もり):
  - 単勝: 判断スナップショットに対する確定オッズの比の 10 パーセンタイルを、**その馬が単独で 1 着だった場合**に限って推定 (勝ち馬は締切直前に売れて下がりやすい)。
  - 複勝: 確定 Lo / 判断時 Lo の 10 パーセンタイルを、**その馬が支払対象だった場合**に限って推定 (複勝の払戻は確定 Lo 以上なので控えめ側)。
  - 帯: 判断時オッズ [1,3) [3,5) [5,10) [10,20) [20,50) [50,100)。q ≤ 1 に切り、帯の間で単調にする。件数の少ない帯は年をまとめる。
  - **推定期間は評価年と重ねない**: バックテスト用 2015-2022、本番用 2015-2024 (+ ライブのログ)。表のメタデータに期間を書き、バックテストは評価年と重なる表を拒否する。

**パーサの規則**
- 結果ページは `<diary_snap_cut>` タグが 25 列中 12 列を包んでいる → 解析前にタグを除去し、列はヘッダ文字列で対応付け。ヘッダと全行が 25 セルであること、必須列 (着順, 馬番, タイム, 着差, 通過, 上り, 単勝, 人気, 馬体重, 調教師, 賞金) がそろうことを検査し、欠けたらそのページを失敗にする (0 や '' で埋めない)。
- 天気は Icon_Weather の title、馬場は span.Item04 (旧来の「天候:」ラベルは消えた)。
- 名前で結合しない (ID で結合)。EUC-JP は `errors="replace"`。

**record 形式への変換器** (`netkeiba → record_data 47 列`): 18 桁 race_id、TARGET 式 class_code、JV track_code (芝ダ + 回り + 内外)、age_code、weight_code、corner_num (履歴のコース表)、time_diff 秒、Ave_3F/PCI/-3F差 は式で再計算 (2025 データで完全一致を確認済み)、error_code (取消→1, 除外→3, 中止→4, 失格→5, 降着→7、着順は降着後)、last_3F_rank は min 順位、父・母・ブリンカーは **shutuba_past** から (結果ページには無い)。

**変換器の合格ゲート (大量クロールの前に必須)**: 2025-09-06〜09-15 (record_data と重なる 2 週分) を取得・変換し、leg 以外の全列が record_data と 100% 一致することを確認する。

**fixture** (保存 HTML、テストで使う): 1 着同着 202304010810 / 3 着同着 202307020512 / 取消 202306010106 / 除外 202307010204 / 中止 202306010103 / 降着 202304040405 / 5〜7 頭立て 202307010311 / 8 頭登録 7 頭出走 202309040202 / 障害 202306010208 / G1 202305010811 / L 202306010110。開催日の当日分 (レース前の一覧・体重発表前の出馬表・取消馬・初出走馬・確定直後の結果) はドライラン日に採取する。

**クローラ**

- `horse_master` 表 (馬 ID → 馬名, 性, 生年, 父, 母, 出典): record_data で初期化し、shutuba_past で更新。

### 3.4 払戻・精算データ

- `payouts.parquet`: (race_key, bet_type ∈ {win, place}, horse_num, payout_per_100, n_paid_places, source, fetched_at)。結果ページの払戻表から。
- 単勝は確定オッズ × 100 と一致するはず (同着を除く) → テストで検査。同着・特払いは払戻表の値。
- 複勝の当たり判定と金額は払戻表 (ラベル規則ではなく)。8 頭登録 7 頭出走 (202309040202) で 2 着払いか 3 着払いかを確認し、判断時の支払着数の決め方に反映する。
- 返還: 判断後に取消・除外になった馬 (error_code 1/3) の券は返還 (賭け金が戻る)。
- 払戻表が欠けた・解析できなかったレースがある**日は丸ごと**バックテストから除外し、件数を報告 (変則的なレースに偏って欠けるのを防ぐ)。

## 4. 特徴量 (約 390 列)

### 4.1 原則

- **判断時刻 (発走 6 分前) に分かることだけで作る**。
  - 馬の過去走: 同じ馬の前走以前 (同じ馬が同じ日に 2 回走ることはないので shift(1) で安全)。
  - **騎手・種牡馬・母父・母・コース基準時計・騎手 Elo などの状態はすべて「前日終了時点」(D−1)**。(entity, date) に集計 → 累積 → 1 日ずらして結合。同じ日の先のレース結果は使わない (ライブでも再現できるように)。
  - 平滑化の事前分布・Elo の K と初期値は 2004 年より前のデータで決めて固定。
  - オッズ: 判断スナップショット (T-6) とそれ以前 (T-120/60/30) のみ。確定オッズ・確定人気・区分 3/4 は禁止。
- **判断時点の出走馬集合 `field_dec`**: 判断スナップショットで単勝オッズが付いている馬 (無ければ error_code ∉ {1,2} の馬)。出走頭数特徴量・馬番/頭数・斤量偏差・レース内の順位/z 値・市場確率の正規化・判断時の支払着数 (field_dec ≥ 8 なら 3、5〜7 なら 2) はすべて field_dec で計算する。**error_code (レース後に決まる除外) を特徴量に使わない**。ラベルは実際の出走馬で作る。
- 2 段階の作成 (メモリ 8GB のため):
  - **段階 A (全履歴・少数列)**: history.parquet から必要な約 30 列だけ読み、特徴量グループごと (1 グループ ≤ 約 120 列) に全期間で計算 → Float32 → `features/{group}/year={Y}.parquet` (Y ≥ 2003) に書いて解放。状態表 (entity × date の累積数、Elo の日次表、各馬の直近 10 走) を `state/` に保存。**この状態表がライブの「前日までの集計表」になる**。年ごとに切って計算してはいけない (前走の 15%・5 走前の 65% が欠ける)。
  - **段階 B (年ごと・小さい)**: 年 Y の各グループとオッズスナップショットを結合し、field_dec 上のレース内相対特徴量を計算 → `features/year={Y}.parquet`。
- ライブでは段階 A (前日までの状態 + 出走馬の過去走) を朝に作り、**段階 B (オッズ・馬体重・出走馬集合・騎手・斤量・馬場/天気・レース内相対) は判断時刻にそのレースの最新の出馬表から作り直す**。
- 実装は polars。並び順は (date, race_key, horse_num) を明示 (CSV は場順)。全特徴量 `.cast(pl.Float32)`。
- カテゴリは学習期間で固定した語彙のコード (Float32)。LightGBM には少数の名義変数 (場・天気・芝ダ) だけ categorical_feature として渡す。騎手 ID・種牡馬名などの高カーディナリティ ID は特徴量に入れない (as-of 統計で置き換える)。
- 欠損は NaN (0 埋め禁止)。オッズは欠損フラグ付き。
- 特徴量レジストリ: (名前, グループ, 元列, dtype=Float32, 段階 A/B, 作る関数)。テストで「元列にレース後情報が無い」「全列 Float32」「キー列 (race_id, 馬 ID) が行列に入っていない」を検査。

## 9. 投票: Goal-reaching (PDF 方式)

### 9.1 1 日のセッション

- 朝に予算 x0・目標 A (> x0)・最大回数 k0。既定 **10,000 円 → 20,000 円、k0 = 3** (o* ≈ 4.85。PDF の運用域 4.7〜4.8 倍に近く、モデルが比較的確かな帯)。`day start` で §0 の表 (P*、上限、期待値、全損の日の割合) をその日の値で表示する。
- 実効の残り回数と判断可否 (**未確定の賭けは同時に 1 つまで**):
  - レース j を判断してよいのは、それまでに買ったすべての券が判断時刻 t_j までに精算済みのときだけ (バックテスト: そのレースの区分 4 時刻 + 2 分 ≤ t_j。ライブ: 払戻を取得済み)。そうでなければ「保留のため見送り」(k は減らさない)。3 場開催の日は直前のレースが未確定のことが多い (2023-24 で約 47%)。
  - `k_eff = min(k, chain_len(j))`。chain_len は残りレースを、前に選んだレースの発走 + 12 分以降に判断時刻が来るものだけ順に貪欲に数えた長さ。
  - 賭け金の上限は手元の資金 (未精算の賭け金を除く)。
  - 1 場だけのセッション `day start --venue` も選べる (同じ場の直前レースは必ず確定している)。
- 終了条件: 資金 ≥ A、k = 0、資金 < 100 円、当日の残りレースなし。
- すべての見送りを理由付きで記録: 保留 / ゲート不通過 / 実現不能 / オッズ欠損 / 締切超過。

### 9.2 理論 (PDF 9 枚目)

現在資金 x、目標 A、残り回数 k、控除率 c (単勝・複勝 0.20):
- 不足率 r = (A − x) / A、狙う有効オッズ o*_k = 1 / (1 − r^(1/k))、公正な的中確率 p* = (1 − c) / o*_k、到達確率 P*_k = 1 − (1 − p*)^k、bold stake s = (A − x) / (o − 1)。
- ガード: x ≥ A は終了、x < 100 または k = 0 は終了、r ≤ 0 で r^(1/k) を計算しない。
- o*_k が外れても変わらないのは丸めない厳密な bold stake のときだけ。**毎レース、実際の資金から o*_{k_eff}(x) を計算し直す** (PDF の実例も 4.793 → 4.767 → 4.737 と動いている)。
- 上限: 1 円あたりの払戻率が ρ = 1 − c 以下の賭けしかしない限り、**P(到達) ≤ 1 − (1 − x/A)^ρ ≤ x/A**。これは単体テストで検査し、`day start` に表示する。実行時の停止条件にはしない (モデルが EV > 1 と言う場面で誤作動するため)。モデルの EV > 1 は「モデルはエッジがあると言っている (資料はどちらもそれを支持していない)」と表示する。

### 9.3 買い目の決定 (PDF 10 枚目)

1. **候補**: field_dec の各馬の単勝・複勝。確率 p̂ は校正済み (単勝は正規化済み)。
2. **オッズ**: 判断スナップショットの o (複勝は Lo)。下落補正 õ = o × q(券種, 帯) (§3.2)。
3. **除外**: 判断時の単勝オッズが 100 倍以上の馬は単勝・複勝とも候補から外す。オッズ欠損。同じ馬の単勝と複勝は片方だけ。**乖離ガード**: p̂ / p_mkt > R_max の券は外して記録 (p_mkt は判断時の市場確率。R_max = 2 から始め、2022 の校正結果で決める。2026-09-21 阪神 11R の「単勝 62 倍に勝率 28%」型の暴走を止める)。
4. **的中確率 P_hit(B)** (重なりを補正):
   - 1 着は p̂_win どおり、2〜m 着 (m = field_dec が 8 以上なら 3、それ以外 2) は 1 着馬を除いた残りから**別の強さベクトル v** の Plackett–Luce で決まるモデル。
   - 複勝確率を射影: p_plc ← clip(p_plc + t, p_win + 1e−6, 1)、t は二分法で Σ = m になるよう。
   - v を反復で合わせる: v ← p_win から始め、v ← v·((p_plc − p_win)/(現在の値 − p_win))^0.7 を正規化しながら max 誤差 < 1e−4 まで (上限 2,000 回)。
   - 全順序 (a,b,c) を列挙 (18 頭で 4,896 通り、m=2 は 2 頭組): 確率 = p_win,a · v_b/(V − v_a) · v_c/(V − v_a − v_b)。P_hit(B) = a が B の単勝に含まれるか、上位 m 頭のいずれかが B の複勝に含まれる順序の確率の和。モンテカルロは使わない (決定的・高速、レースごとにキャッシュ)。
   - 実行時の検査: max p̂_i ≤ P_hit ≤ min(1, Σp̂_i)、券 1 枚のバスケットは p̂ を正確に再現。単勝だけのバスケットは Σp̂ と一致。
5. **金額 (100 円単位、どれが当たっても目標に届く)**: n_i ← ceil(((A − x) + 100·Σn) / (100·õ_i)) を変化しなくなるまで繰り返す (Σ1/õ < 1 なら単調に収束)。100·Σn > x なら**そのバスケットは実現不能** (上限で切らない)。配分後に o_eff_real = min_i(s_i·õ_i)/Σs、EV、P_hit を計算し直す。
6. **選び方**: o_eff_real が帯 **[o*_{k_eff}, 1.10·o*_{k_eff}]** に入り、実現可能で、EV_goal ≥ τ のバスケットのうち P_hit 最大 (PDF の実購入は o_eff / o* = 1.031〜1.034 で帯の中)。探索: 候補を p̂·õ の降順に並べた上位 12 枚から、同一馬の単複を避けた 4 枚以下の全組合せ (793 通り、列挙済みの順序表で 50 ms 未満)。k_eff = 1 では帯の下限 o*_1 = A/x がそのまま「1 回で届く」条件になる。
7. **ゲート**: EV_goal = P_hit(B) · min_i(s_i·õ_i) / Σs_i ≥ τ (0.8)。重なった複勝の二重当たりは目標到達に寄与しないので、払戻の期待値ではなくこれで判定する。通常の EV (Σp̂õs/Σs) と生オッズでの EV も記録する。ゲートを通るのは「モデルがバスケットを市場より約 20% 以上高く評価する」ときだけで、複勝 Lo × q では複勝はほとんど通らない (実質は単勝中心になる。PDF の実購入も単勝のみ)。
8. **表示前の安全ゲート** (PDF の安全ゲートの推奨版): 判断スナップショットが official_datetime で 90 秒以内、現在時刻 ≤ 発走 − 3 分、バスケットの全馬が最新オッズでまだ売られている、Σs ≤ x、丸め後の o_eff・的中時資金・EV を再計算済み。どれか失敗なら推奨を出さず理由を記録。
9. **出力**: 買い目 (券種・馬番・金額)、o*_k、o_eff、P_hit、EV_goal、P*_k、当たった場合の資金、上限 1 − (1 − x/A)^0.8。

### 9.4 モジュール

- `betting/theory.py` (式・上限) / `betting/joint.py` (2 段 PL の当てはめと順序表) / `betting/allocate.py` (100 円単位の配分) / `betting/basket.py` (候補・除外・探索・ゲート) / `betting/session.py` (イベントソース型の状態) / `betting/settle.py` (精算・返還)。純粋関数で、ネットワーク・ファイル I/O から分離してテストする。

## 10. バックテスト

- 期間: 開発 2023 (q 表は 2015-2022)、封印 2024 (最後に 1 回)。開催日ごとに 1 セッション。判断時刻 t_j = 発走 − 6 分 (2023-24 はクロールした発走時刻、同順は (発走, 場, R))。精算時刻 = 区分 4 時刻 + 2 分。§9.1 の「未確定は 1 つまで」を同じく適用し、保留で止められた回数を報告。
- 候補・正規化・支払着数は判断時に分かる情報 (判断スナップショットでオッズが付いている馬) だけで作り、error_code は使わない。
- 精算: 返還 (取消・除外) → 払戻表の値 → 0。券の一部が返還されても、返還されなかった券が 1 枚でもあれば k を減らす。当たり券の「実際の払戻 / 計画の払戻」を報告。
- **τ = 0.8、q = 10 パーセンタイル、帯 [o*, 1.10·o*]、k0 は PDF の値で固定し、調整しない** (213 日分のセッションでは到達率の差 4 ポイントを検出する力が 15% しかない)。
- **主指標 (レース単位、状態を固定して標本化)**: 判断可能な各レースで、状態 x/A ∈ {0.2, 0.33, 0.5, 0.8} × k ∈ {1, 3, 6} の推奨バスケットを計算し、
  - 予測 P_hit と実際の的中の比較 (o_eff 帯別の校正)
  - 実現した目標到達リターン Σ1{的中}·(最小払戻)/ΣS
  - 付加価値 ΔV = 平均[1{到達} + (1 − 1{的中})·P*_{k−1}(x − S)] − P*_k(x)
  - 比較対象との差を開催日ブロックのブートストラップ CI で。
- 副指標 (セッション): 到達率 (Wilson 95% CI)、最終資金の平均・中央値 (セッション単位ブートストラップ CI)、購入回数、検出力の表。到達率の Wilson 下限が平均 x0/A を超えたら「先読みの疑い」として警告。
- 比較対象 (同じ日・同じ摩擦 (q・切り上げ・保留) で):
  - (a) 毎レース見送り
  - (b) 判断時 (T-6) の 1 番人気の単勝に bold stake
  - (c) モデル Top-1 の単勝に bold stake
  - (d') **オッズ由来の特徴量だけ**で同じパイプライン (5 seed → Isotonic → 正規化) を作ったモデルで同じ方策 — モデルの寄与の切り分け。主比較は「本モデル vs (d')」を τ なし (実現可能なら必ず買う) で行い、τ = 0.8 の結果は別に報告 (ゲート通過率、通過したバスケットの予測 EV と実現)。
  - (e) 市場確率で帯 [o*, 1.15·o*] の実現可能なバスケットを無作為に選ぶ (エッジなしの基準・シミュレータの健全性確認)
- ゲート診断 (§9.3-7 の検証): レースごとの通過率、通過した券の p̂/p_mkt の分布、その実際の的中率が p̂ と p_mkt のどちらに近いか (p_mkt に近ければゲートは「モデルの誤り」を選んでいる)。

## 11. ライブ運用 (普通の開催日)

CLI (`keiba-goal`):

| コマンド | 内容 |
|---|---|
| `keiba-goal data update` | 前回以降の結果・shutuba_past を補完 (history, payouts, horse_master, state を前日まで更新)。前の開催日が全レース揃っているか検査 |
| `keiba-goal train [--stage P5a..P5e]` | 7 章 (段階ごとに再開可能) |
| `keiba-goal evaluate [--sealed]` | 8 章 |
| `keiba-goal backtest --budget 10000 --goal 20000 --bets 3 [--sealed]` | 10 章 |
| `keiba-goal day start --budget 10000 --goal 20000 --bets 3 [--venue 中山]` | 事前チェック → セッション作成 → その日の P*・上限・期待値・全損の日の割合を表示 |
| `keiba-goal day run` | 常駐 (下の状態機械) |
| `keiba-goal day status` | 状態表示 |
| `keiba-goal day record --race <12桁> --tickets "win:5:500,place:7:300" \| --none \| --payout N \| --balance N` | 訂正イベントの追記 (購入内容・払戻・実残高の同期) |
| `keiba-goal predict --race_id <12桁>` | 1 レースの確率表 (買い目なし、そのレースの日付より前の履歴だけ使う) |

**day start の事前チェック**: `data update` で前日分まで取り込み済み (履歴の最大日付 < 今日)、モデルと段階 A の特徴量を読み込み、省電力モード・空きメモリの表示、PID ロック (`train`・クロールはロック中は動かない)、最初の発走の 125 分前までに開始していること (遅れた場合 T-120 が無いレースは推奨しない)。

**day run の状態機械** (5 秒以下の壁時計ティック、長い sleep はしない。`caffeinate -i -s -w <pid>`):
- 各レース: `WAITING → POLLING (発走−130〜−2 分、5 分ごとにオッズ保存) → DECIDING (−8:00 shutuba_past 再取得、−6:00 判断オッズ、段階 B 作り直し → 推奨) → SHOWN (−5:00 までに表示) → 確認待ち → BOUGHT / NOT_BOUGHT → PENDING (発走 +6 分から 60 秒ごとに結果を確認) → SETTLED`。−3:00 を過ぎたら判断しない (MISSED)。
- 体重が欠けている出走馬がいたら −6:30 に再取得、それでも欠けていれば見送り。
- **オッズの採否**: `status == "middle"` かつ official_datetime が目標時刻の鮮度上限内のものだけ使う。yoso (予想オッズ) と result (確定) は使わない。`predict` で既に確定したレースは保存済みスナップショットを使うか拒否する。収集したスナップショットは `live_odds/` に §3.2 と同じ形で保存し、2026 年以降の評価データにする。
- **購入の記録**: 推奨を表示したら端末で b (表示どおり買った) / n (買わなかった) / e (券を編集) を入力。既定値は無い。発走時刻までに未確認なら UNCONFIRMED とし、解決するまで以後の推奨を止める。
- **セッションはイベントソース**: `sessions/{date}/events.jsonl` に追記のみ (flock + fsync)、状態は毎ティック events を畳み込んで作る。冪等キー (race_id, step)。`day record` は訂正イベントを追記するだけ。
- 復帰: 30 秒以上の時刻の飛び (スリープ明け) や再起動では、レース一覧を取り直し (発走時刻変更・中止)、過ぎた締切は MISSED にする。
- 精算: race.netkeiba.com の結果ページ (形式はドライラン日に採取、予備は db ページ) を発走 +6 分から 60 秒ごと。払戻が出るまで PENDING で、§9.1 により次の判断を止める。手動 `--payout` も可。
- 遅延の検査: 段階 B + 予測 + バスケット計算が M2 で 10 秒以内 (P7 のテスト)。

**ドライラン日 (本番運用の前に 1 回)**: レース前の一覧、体重発表前の出馬表、取消馬、初出走馬の体重欄、yoso/middle のオッズ JSON と official_datetime の遅れ、確定直後の結果・払戻ページ、JRA の発売締切 (公表は発走 2 分前、config 値) を採取・確認する。

## 12. テスト

pytest、ネットワークなし (netkeiba は保存 HTML の fixture)。全体で数秒 (as-of テストは 3 場 × 18 か月程度の小さな fixture で)。
1. record 読み込み: dtype、最新スナップショットのみ、race_id 分解、同着の着順。
2. T-x 抽出: 区分 3/4 を使わない、最初の区分 3、票数 97% 以上の行を捨てる、全 T-x 行の票数比 < 0.97 かつ時刻 ≤ close_est、鮮度と欠損。
3. 変換器: ゲート窓で record_data と完全一致、fixture の各ケース (同着・取消・除外・中止・降着・少頭数・障害・G1/L)、`<diary_snap_cut>`、払戻表、単勝払戻 = 確定オッズ × 100 (同着以外)。
4. 特徴量の as-of: 日付 D をサンプルし、D より後の行を消し、D の行のレース後列を空にして作り直しても D の特徴量が変わらない。全状態が D−1。母の ID 解決が子の生年より後の行を使わない。レジストリ検査 (禁止列・Float32・キー列なし)。パリティ P1〜P3。
5. 目的変数: 出走頭数、同着、≤4 頭の除外。
6. CV: FLAML・Optuna が実際に使った全分割で 学習最大日付 < 検証最小日付、race_key の重なりなし。
7. Goal-reaching の式: PDF の値 4.7930 / 72.1485% / 4.7671 / 4.7370、P*_k ≤ 1 − (1 − x/A)^0.8 ≤ x/A (c = 0 で等号)、厳密な bold stake でだけ o* 不変、ガード。
8. 配分: min_i s_i·õ_i ≥ A − x + Σs、Σs ≤ x、100 円単位、最小性 (どれか 1 つ減らすと条件を破る)。PDF 11 枚目 10R の再現 (x = 1,694,430, A = 2,440,000, k = 5, 11 番 T-5 オッズ 8.4, q ≈ 0.787 → 的中で 2,440,000 に届く)。
9. 2 段 PL: 周辺確率が入力と 1e−4 以内、券 1 枚で p̂ を再現、単勝だけなら Σp̂。
10. セッション: 2 場が 10 分おきに発走する日で、各判断の x と k に判断時刻までに精算された券だけが入っていること、UNCONFIRMED で止まること、返還時の k、イベントの畳み込みの冪等性。

## 14. 主なリスク

- **市場に勝てない**: オッズ込みのモデルは市場とほぼ同じ意見になり、ゲート (EV ≥ 0.8) を通るのはモデルが市場と食い違う場面 = 誤りやすい場面に偏る。ゲート診断 (§10) で必ず確かめる。
- **計算資源**: P5 は 16〜20 時間以上。段階制・時間上限・保存/再開で抑え、修正ループは P5a だけで回す。
- **2025 年以降のオッズ時系列が無い**: オッズ込みモデルの直近評価はできない。ライブ収集分で後から評価する。
- **netkeiba**: 規約・負荷・レイアウト変更 (既に一度変わっている)。間隔 2.5 秒以上、manifest、fixture テスト、件数の検査で壊れたら止める。
- **時刻の取り違え**: 学習の「T-6」とライブの「発走 6 分前」のずれ、締切後の行の混入は §3.2 のガードとパリティ P1 で防ぐ。
- **払戻の欠落**: 複勝の実払戻はクロールでしか得られない。欠けた日は推定で埋めずに除外して報告。
- **調教師・厩舎の統計が v1 に無い** (SpeakerDeck の改良モデルとの差)。窓 3 のクロール (約 48 時間) の可否はユーザー確認事項。
